# 프로젝트 작업 기준

- 이 저장소에서 작업하기 전에 docs/DEVELOPMENT.md와 docs/STORY.md를 읽는다.
- DEVELOPMENT.md는 현재 구조·화면·이동·충돌·저장·확장 규칙,
  STORY.md는 현재 이야기·대사 분기·이벤트 플래그를 관리한다.

- 사용자의 최신 명시적 요구를 최우선으로 한다.
- 코드와 문서가 다르면 실제 동작을 확인하고,
  이미 구현된 사실과 새로 요청된 방향을 구분하여 갱신한다.

- 사용자가 승인한 Nintendo DS DP/플라티나풍 비주얼 방향을 유지한다.
- 현재 요청하지 않은 기능, 지역, 시스템, 장기 스토리를 추측해서 선행 구현하지 않는다.

- 기존 시스템을 불필요하게 재작성하지 않는다.
- 관련 없는 코드나 다른 세션의 작업을 임의로 정리·리팩터링하지 않는다.
- 기존 ID, 이벤트 플래그, 포켓몬 데이터 ID와 유효한 저장 진행을 가능한 한 보존한다.

- 동작·맵·포켓몬 데이터·저장 계약·스토리 구조가 변경되면 관련 문서도 함께 갱신한다.
- 중요한 새 규칙이 확정되면 코드에만 남기지 말고 DEVELOPMENT.md 또는 STORY.md에 반영한다.

- 변경에 적절한 테스트와 `npm.cmd run build`를 실행한다.
- 플레이 동작을 변경했다면 실제 브라우저에서도 해당 동작을 확인한다.
- 자동 테스트 성공과 실제 플레이 검증 성공은 구분해서 판단한다.

- 브라우저 QA는 고유한 `?qa=이름`을 사용하여 사용자 저장과 분리한다.
- QA 과정에서 사용자의 실제 진행 데이터를 수정하거나 초기화하지 않는다.

- 구현이나 수정 후 기존 기능에 영향을 줄 가능성이 있다면 관련 회귀 테스트도 수행한다.

- 작업 완료 시 과도한 설명 대신 다음을 명확하게 남긴다.
  1. 변경한 내용
  2. 테스트한 내용
  3. 남은 문제 또는 미검증 항목

## 자율 개선 원칙

- 사용자는 2026-09-07부터 담당 영역의 자율 점검과 개선을 승인했다. 명시적인 개별 구현 요청이 없어도 현재 프로젝트에서 명확한 버그, 기존 기능의 미완성, 일관성·UX·구조적 문제를 확인하면 합리적인 범위에서 직접 개선한다.
- 단순히 개선 가능성을 보고하는 데 그치지 않는다. 위험이 낮고 요구사항이 명확한 문제는 원인을 확인하고 수정·구현·검증까지 마친다.
- 영향도와 필요성으로 우선순위를 정하고, 한 차례에 가장 중요한 1~3개만 끝낸다. 문제가 없으면 억지로 변경하지 않는다.
- 아직 결정되지 않은 스토리·지역·시스템·디자인을 임의로 확정하지 않는다. 초안이나 미구현 목록에 있다는 이유만으로 새 시스템을 선행 구현하지 않는다.
- 다른 담당 영역에 큰 영향을 주는 변경은 문제·근거·영향을 인계 기록에 남겨 총괄이 배정한다. 기존 구조를 더 깔끔하게 보이게 하려는 대규모 리팩터링은 하지 않는다.
- 변경 후 관련 테스트와 빌드를 실행한다. 플레이 변경은 고유한 QA 저장으로 실제 브라우저에서 다시 검증한다. 환경 때문에 검증하지 못했다면 미검증으로 기록하고 완료로 처리하지 않는다.
- 확정된 동작과 문서는 함께 갱신한다. Story 담당의 설계 보완은 현재 구현 사실과 구분하여 기록하며 코드 반영 전에는 런타임 구현 완료로 쓰지 않는다.
- 완료 보고에 변경·검증·남은 문제와 우선순위가 높은 다음 후보를 간단히 남긴다.

## 다섯 담당 작업의 자동 운영

- 역할·순환 순서·인계 방식은 [AUTONOMOUS_WORKFLOW.md](AUTONOMOUS_WORKFLOW.md)를 따른다.
- 총괄 작업이 [PROJECT_STATE.md](PROJECT_STATE.md)의 배정을 관리한다. 같은 폴더에서 자동 개선을 수행하는 담당자는 한 번에 한 명이다.
- 역할 설정 메시지는 실행 배정이 아니다. 총괄의 회차 ID가 있는 실행 요청을 받은 담당자만 해당 회차의 수정·테스트를 진행한다. 사용자의 직접 요청은 우선하되 기존 배정과 겹치면 총괄이 새 자동 배정을 보류한다.
- 담당자는 자신의 회차를 마친 뒤 결과를 남기고 응답을 종료한다. 다음 담당 호출과 다음 회차 시작은 총괄이 맡는다.
