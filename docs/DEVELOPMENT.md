## 1. 책임과 적용 범위

이전 제0절과 도시 완료 조건으로 연결한 문서는 [콘텐츠 제작 기준](MAP_STORY_DESIGN.md)을 따른다.
작업 대상 선정은 [실행 로드맵](STORY_AXIS_ROADMAP.md), 현재 상태 판정은 [PROJECT_STATE](PROJECT_STATE.md)가 담당한다.
문서 재정립 이후 게임 구현에 착수했다. 코드 변경과 실제 사용자 저장·서버·자동화 조작은 구별하며 이번 구현에서 실제 저장은 읽거나 수정하지 않는다.
QA 중단을 유지한다. 테스트·빌드·브라우저 플레이·시각/음향·저장 검증의 재개는 별도 명시가 필요하다.
후속 구현의 완료 조건에 적힌 검사는 재개 후 수행할 조건이며 지금 실행하라는 지시가 아니다.

## 2. 기술 선택: HYBRID

**기존 런타임을 유지하고 첫 제작 구간에 필요한 계약을 점진 교체한다.** 새 저장 스키마와 별도 게임 엔진 재작성은 다른 결정이다.
기존 파일을 모두 현행 설계로 채택하지 않는다. 필요한 구현을 선별하되 미채택 구현도 근거 없이 삭제하지 않는다.

| 대안 | 장점 | 현행 판단 |
|---|---|---|
| KEEP: 기존 계약을 그대로 확장 | 즉시 콘텐츠 추가 가능 | 4배지·Lv25·기존 스타팅 검증과 새 정사가 충돌하므로 단독 채택 불가 |
| HYBRID: 기존 실행체 안에서 호환 이행 | 이동·전투·회복·도시 자산을 활용하고 구간별 교체 가능 | 채택. 저장 보호를 먼저 두고 한 여정에서 효용을 확인 |
| V2: 별도 실행체로 재작성 | 구조를 자유롭게 설계 | 현재 채택하지 않음. 재구현 비용과 기능 누락 위험을 상쇄할 증거가 없음 |

근거는 [저장 파서](../src/save.ts), [엔진](../src/engine.ts), [맵 조립](../src/maps.ts), [전투](../src/battle.ts)다.
새 프레임워크·범용 퀘스트 언어·전체 폴더 재배치부터 시작하지 않는다. 첫 구간에 쓰이는 작은 경계부터 만든다.
전투·저장·이벤트·콘텐츠 등록 구조를 정할 때는 [적극 참고 기준](reference/REFERENCE_RESEARCH.md)의 관련 저장소와 현재 코드를 대조한다. Showdown·Essentials·RPG-JS·pret·expansion 등의 관련 정의·소비 경로를 검토하고, 채택하거나 달리 설계한 이유를 해당 계약에 남긴다. 외부 구조를 그대로 따라야 하는 것은 아니다.
기존 실행체에서 요구 기능을 수용할 수 없다는 구체적 증거가 생길 때만 V2의 기능 대응표·이행 비용·복귀 방법을 다시 비교한다.

## 3. 현재 구조와 허용 의존 방향

아래 표는 현재 파일의 역할이다. 이미 분리된 완성 아키텍처라는 뜻은 아니다.

| 역할 | 현재 진입점 | 보존하거나 분리할 경계 |
|---|---|---|
| 시작·입력·프레임 | `main.ts` | 입력 전달, 포커스, 프레임 실행과 리소스 로드 |
| 실행 조정 | `engine.ts` | 이동·대화·패널·전투의 상태 전이와 저장 호출 |
| 지도 정의·조립 | `explore-world.ts`, `maps.ts`, `unified-world.ts` | 정적 배치, 구 ID 별칭, 현재 저장에 따른 지도 투영 |
| 콘텐츠 행동 | `city-activities.ts`, `journey-services.ts`, `sinnoh-story.ts`, 지역 모듈 | 지도·이벤트에 해당하는 대화, 선택, 상태 변화 |
| 전투·성장 | `battle.ts`, `pokemon.ts`, `growth.ts`, `move-pp.ts` | 계산, 참여 개체, 결과와 연출 프레임 |
| 표현 | `renderer.ts`, `audio.ts`, 지역 미술 모듈 | 실행 상태를 읽어 화면과 음향으로 표현 |
| 저장 | `types.ts`, `save.ts`, `save-library.ts` | 검증·이행·복원·파일 입출력 |
| 정적 자료 | `data/*`, `runtime-pokemon-data.json` | 카탈로그, 원자료 출처, 실행 지원 범위 |

새로 분리하는 코드의 값 의존 방향은 `실행 조정 → 콘텐츠/전투/저장 서비스 → 순수 규칙·정의`로 둔다.
지도 조립기는 배치·등록 자료를 읽고, 순수 정의와 플래그 상수는 지도 레지스트리·엔진·렌더러를 역참조하지 않는다.
렌더러는 실행 결과를 읽되 보상·배지·스토리 완료를 직접 기록하지 않는다. 화면 표시를 사건 발생 근거로 쓰지 않는다.
기존 지역 모듈이 `Engine`을 `import type`으로 받는 것은 점진 이행 중 허용한다. 타입 의존과 실행 시 값 순환을 구분한다.
`trainer-flags.ts`의 의존성 없는 키 정의를 유지한다. 이곳에 `maps`나 지역 모듈을 재연결하지 않는다.
거대한 핸들러는 담당 구간을 옮길 때만 분리한다. 기존 처리 순서·중복 차단·폴백을 어댑터로 유지한다.

## 4. 유지해야 할 실행 동작

### 이동·워프·지도

- 저장 좌표는 한 타일 이동이 확정될 때 갱신한다. 이동 애니메이션 중 좌표와 확정 좌표를 혼용하지 않는다.
- 문은 `entry` 방향으로 진입하고 목적지 `spawn`과 `facing`을 적용한다. 출구 타일만 맞추어 양방향 이동 완료로 판정하지 않는다.
- 워프 전환 중 입력을 비우고 완료 뒤 저장한다. 이동·전환 중 새 대화나 메뉴가 중첩되지 않게 현재 잠금 계약을 보존한다.
- 충돌·NPC·예약 칸·풀밭·출구와 시각 표현은 같은 배치를 가리킨다. 그림에만 길이나 상호작용 대상을 추가하지 않는다.
- `getMap(id, flags)`의 동적 NPC·장애물·수거물 변화는 해당 저장의 투영이다. 공유 기본 맵을 플레이 중 영구 변경하지 않는다.
- `WORLD_ALIASES`와 기존 MapId는 저장 이행 입력이다. 표시명 정정이나 지리 확장 때문에 기존 저장 키를 재사용하지 않는다.

### 대화·취소·동료·보상

- 선택 대화의 현재 취소는 마지막 선택지를 실행한다. 마지막 선택지에는 거절·돌아가기 동작을 두고 보상·완료를 숨겨 넣지 않는다.
- 일반 문장과 전투 연출에서 취소 키가 다음 페이지로 진행하는 현재 동작을 임의로 바꾸지 않는다. 변경 시 입력 계약을 함께 고친다.
- 늦게 실행된 콜백은 시작 시점의 저장 객체·맵·장면과 현재 상태를 대조한다. 다른 저장을 불러온 뒤 이전 보상이 적용되면 안 된다.
- 완료·보상은 각각 명시하고 한 번만 지급한다. 관찰·생활 플래그를 새 본편 장면이나 배지 완료로 간주하지 않는다.
- 실제 동료를 요구하는 행동은 파티 객체를 추적한다. 같은 종의 다른 개체나 교체된 슬롯을 자동으로 같은 동료로 인정하지 않는다.
- 취소·패배·동료 기절·파티 이탈 후 재진입을 설계한다. 선택 활동이 기존 도시 출입·회복·귀환을 잠그지 않게 한다.

### 전투·성장·표현

- `battleTurn()`의 결과와 `TurnResult.frames`를 유지한다. 대사 페이지의 HP·개체·피해 연출은 해당 프레임을 읽는다.
- 계산 결과를 먼저 표시하거나 마지막 HP를 모든 페이지에 재사용하지 않는다. 연출을 위해 전투 계산을 다시 실행하지 않는다.
- 전투 참여·직접 격파·포획·도주·패배를 구분한다. 실제 종료 결과 없이 지역 활동의 실전 완료를 기록하지 않는다.
- 기술 PP는 현재 플레이어 기술 실행 시 소모한다. 행동 전에 쓰러진 기술, 취소·거부된 선택에 소모를 붙이지 않는다.
- 현재 단순화한 HP·경험치·포획·기술 지원 규칙은 호환 계약이다. 원작 전면 재현으로 보고하지 않고 바꿀 때 영향과 이행을 기록한다.

## 5. 저장 계약과 안전한 이행

### 현재 제약: 후속 제작 전까지 보존

- `SaveData.version=1`, `worldRevision=24`, 기본 키는 `first-partner-save-v1`이다. 버전과 지도 개정은 별개다.
- 파서는 배지 최대 4개와 `GYMS` 순서·TM 일치를 요구한다. `observationCollected → researchDelivered → ferryPass` 의존도 남아 있다.
- 레벨 상한 25, 현재 HP·경험치·지원 기술, 소유 가능 종 목록이 정상 저장 판정에 포함된다.
- 스타팅 판정은 `[1,2,4,5,7,8]` 계열과 `starterReceived`에 연결된다. 새 정사의 스타팅을 문서만 바꾸어 저장할 수 없다.
- 플래그 값은 `boolean | number`다. 문자열·대화 콜백·진행 중 애니메이션을 현재 플래그에 저장하지 않는다.
- 구 MapId 별칭, 누락 필드 보충, 막힌 좌표의 안전점 이동, `checkpoint()`의 안정 위치 처리를 보존한다.
- 포켓몬에는 영속 개체 ID가 없다. 필요할 때 도입하되 기존 파티·박스의 개체와 지역 활동 연결을 함께 이행한다.

### RB1 저장 보호 계약: 코드 반영·실행 미검증

`save.ts`의 `inspectSave()`가 버전을 먼저 판정하고 기존 v1 정규화를 별도 JSON 객체에서 수행한다. 원문은 변환하지 않는다. `parseSave()`의 기존 반환 계약과 v1·revision24·포켓몬/배지 제한은 유지한다. v2 이행을 구현한 것은 아니다.
`save-session.ts`가 저장소 접근·원본·쓰기 허용·활성 사본을 소유한다. Engine 생성자는 이 경계를 연 뒤 기절 복귀를 처리하며, `persist()`를 통한 필드·창 숨김·종료 저장도 같은 쓰기 차단을 따른다.

| 입력 | 코드의 처리 |
| --- | --- |
| 키 없음 | 메모리 새 게임. 첫 저장은 별도 사본 생성·재조회 후 활성화 |
| 정상 v1 / 구 지도 개정 v1 | 기존 정규화·좌표/방문 이행을 재사용. 첫 쓰기 또는 정규화 필요 시 원문 보관 후 별도 활성 사본으로 전환 |
| 손상 JSON·빈 문자열·스키마 불일치 | 원본 문자열을 보관하고 자동 저장 차단. 옛 탐험 저장으로 조용히 대체하지 않음 |
| 미래 저장 버전 / 미래 지도 개정 | 거부 이유를 구별하고 원본 보호·자동 저장 차단 |
| 저장소 읽기 실패 / 활성 대상 누락·포인터 손상 | 빈 저장으로 간주하지 않음. 사본 내보내기와 명시적 복구 안내 |
| 구 탐험 저장만 존재 | 주 저장과 활성 선택이 없을 때만 후보로 읽음. 기존 키에 쓰지 않음 |

`B`는 기본 `first-partner-save-v1` 또는 `?qa=name`의 `first-partner-save-v1:qa:name`이다.

| 키 | 역할 |
| --- | --- |
| `B` / 기존 `first-partner-save-v1:explore[:qa:name]` | 이전 원본. 신규 writer가 덮어쓰지 않음 |
| `B:session:<id>` | 검증한 후보/활성 사본. 활성화 실패 후보도 원본과 분리 |
| `B:active` | `nexus-active-save` v1 선택 정보. 사본 키와 선택 전 원본의 recoveryKey |
| `B:recovery:<id>` | 변환 전 정확한 원문. 자동 삭제하지 않음 |
| `B:library:1..3`, `B:library:backup` | 기존 사용자 슬롯과 한 단계 되돌리기. 활성 사본 키와 독립 |
| `B:library:<slot>:recovery:<id>` / `:recovery-latest` | 읽지 못한 슬롯 또는 유효하지 않은 현재 상태의 원본과 다운로드 참조 |

새 게임·파일·슬롯 불러오기는 `Engine.activateSave()`의 **후보 검증 → 원문 사본 보관/재조회 → 별도 대상 쓰기/재조회 → 활성 선택 쓰기/재조회 → 메모리 복원** 경계를 따른다. 기존 `restore()`는 게임 안 위치 이동용이며 보호 상태를 해제하지 않는다. 슬롯은 비어 있음과 읽기 실패를 구분하고, 실패 슬롯의 명시적 덮어쓰기에도 원문 보관이 먼저 성공해야 한다.
모험 기록 패널에서 보호 이유·원문 다운로드·현재 진행 파일 보관·별도 저장 전환을 제공한다. 이미 유효하지 않은 현재 상태도 복구용 원문으로 보관하여 정상 파일 불러오기를 막지 않는다.

백업/후보 저장 실패는 활성 선택 전 멈춘다. 활성 포인터 쓰기를 시도한 뒤 확인에 실패하면 `activation-uncertain`으로 잠그고 재열기 안내를 낸다. 이 경우 저장소의 선택은 바뀌었을 수 있으며 메모리 복원 성공으로 표시하지 않는다. localStorage 여러 키의 트랜잭션이나 여러 창의 동시 쓰기 완전 차단을 보장하지 않는다. 관측한 포인터·원문 변화는 쓰기 직전 감지해 중단한다.

원작/외부 비교는 [저장 보호 참고 기록](reference/REFERENCE_RESEARCH.md#저장-보호와-활성-사본--2026-09-22)을 따른다. 지도 개정은 위치 호환에, 자료 모양 변경은 향후 명시적 스키마 이행에 사용한다. 종료 조건은 QA 재개 뒤 대표 사본의 읽기·재저장·재접속과 파티·박스·보상·위치 보존이다. 회귀 검사 원고는 `tests/save-session.test.ts`에 준비했으며 실행하지 않았다.

### 새 게임과 기존 저장

새 게임에는 채택 정사의 도입·새 스타팅·본편 진행을 적용한다. 기존 저장의 동료·획득물·성장·실제 완료 기록은 보존한다.
기존 저장에 새 도입을 강제로 재연하거나 기존 파트너를 교체하지 않는다. 과거에 보지 않은 장면을 완료했다고 자동 기록하지 않는다.
기존 저장을 새 본편의 어디에 합류시킬지는 보유 진행과 모순 없는 명시적 연결로 설계하고 [결정 문서](NEXUS_GOAL.md)에 남긴다.
기존 배지·플래그는 의미를 대응시키며, 구 4배지를 32배지 완주나 신오 리그 완료로 승격하지 않는다.
새 저장과 이행 사본은 원본과 분리한 키/슬롯에서 개발한다. 기존 저장을 직접 실험 자료로 사용하지 않는다.

## 6. 정적 자료와 실행 이벤트의 경계

이전 제85절의 반영 현황은 [현재 상태](PROJECT_STATE.md)에서 확인한다. 이 절은 자료를 실행에 연결하는 계약이다.
정적 카탈로그는 종·기술·아이템·조우 풀·맵·목표 조건을 정의한다. 조회만으로 상태·배지·아이템·포켓몬을 지급하지 않는다.
실행 이벤트는 현재 맵과 조건을 확인하고 선택·이동·전투 결과를 받아 상태를 바꾼다. 대사·연출·보상·재진입을 함께 연결한다.
우선 기존 이벤트 핸들러를 명시적 `map + event` 등록으로 옮기는 작은 어댑터를 사용한다. 전체 퀘스트 문법을 선행 제작하지 않는다.
완료 조건은 실제 행동 근거를 읽고 효과는 한 번만 적용한다. `CH/SQ/PG/LEG` 설계 ID의 존재는 실행 이벤트나 완료 기록이 아니다.

자료 경로는 `nexus-plan.json + 고정 원자료 → build_databases.py → 설계 JSON → export-runtime-pokemon.py + runtime-local-pools.json → runtime-pokemon-data.json`이다.
`docs/개발용_초안맵.md`와 `docs/개발용_초안스토리.md`는 현재 생성기가 읽는 입력이므로 경로·표 구조를 임의 폐기하지 않는다. 생성 문서와 입력 문서의 역할을 구분한다.
생성기에 남은 4개 필수 배지 검증과 익스포터의 Lv25 절단은 후속 정합화 대상이다. 새 정사에 이미 맞춰졌다고 보고하지 않는다.
생성 출력만 손으로 고치지 않는다. 원본·생성기·출력·런타임 바인딩·지원 기능과 출처를 함께 대조한다.
자료 범위와 상세 이행 계약은 [RUNTIME_DATABASE](RUNTIME_DATABASE.md)에 통합했다. WORLD_DATA_STANDARDS는 기존 링크의 호환 입구다.

## 7. 지도 통합과 길안내

이전 제47·48절의 현행 계약은 이 절과 [콘텐츠 제작 기준](MAP_STORY_DESIGN.md)을 따른다.
실제 경유 MapId·양쪽 출구·이동 수단·조건·귀환은 [WORLD_ROUTES](WORLD_ROUTES.md), 목표 크기는 [MAP_SIZE_STANDARDS](MAP_SIZE_STANDARDS.md)가 소유한다.
현재 지도, 표지, NPC, 다음 목표 안내는 실제 개통된 이동과 일치해야 한다. 계획된 도로를 이미 걸을 수 있는 길로 안내하지 않는다.
기존 직접 워프를 새 구간으로 바꿀 때는 양끝 좌표·별칭·회복 지점·구저장 귀환을 함께 이행한다. 출입구 그림만 바꾸지 않는다.
길안내는 이동 가능한 경로를 알려 준다. 안내를 읽거나 목적지를 선택한 것을 도착·장면·퀘스트 완료로 기록하지 않는다.

## 8. 가장 작은 교체와 롤백

제작 우선순위와 각 단계 산출물은 [실행 로드맵](STORY_AXIS_ROADMAP.md)이 정한다. 기술 교체는 아래 크기로 제한한다.

1. 현행 계약과 보존 자료를 고정하고 실패 원본 보호를 먼저 구현한다. 저장 대표 사본과 변환 대응표를 준비한다.
2. 첫 제작 구간의 새 게임·기존 저장 진입점을 나누고 필요한 진행 구조를 이행한다. 아직 쓰지 않는 전 지방 시스템을 일괄 제작하지 않는다.
3. 해당 구간의 한 이벤트 또는 한 지도 경계를 어댑터로 옮긴다. 기존 ID·콜백 무효화·보상 단발성과 표현 계약을 유지한다.
4. 입력 데이터부터 해당 구간의 실행 바인딩까지 연결한다. 전투·성장 규칙 확장은 그 여정에 필요한 범위로 묶는다.
5. QA 재개 후 해당 계약과 여정의 결과를 확인하고 새 경로를 기본으로 전환한다. 미검증 교체를 전 지방으로 복제하지 않는다.

각 교체는 이전 처리 경로와 되돌릴 범위를 명시한다. 동일 이벤트의 구·신 처리기가 동시에 보상을 지급하지 않게 한다.
코드 롤백은 변경 묶음 단위로 하고 다른 작업자의 미커밋 파일을 되돌리지 않는다. 데이터 출력은 대응하는 입력·생성기와 함께 복원한다.
저장 롤백은 이행 전 원본 또는 분리된 사본으로 복귀한다. 새 스키마 저장을 구 코드가 이해한다고 가정하거나 강제 하향 변환하지 않는다.
롤백하면서 새 경로의 보상을 구 저장에 합산하지 않는다. 결과·실패·미검증 항목을 [현재 상태](PROJECT_STATE.md)에 남긴다.
도시 완성·여정 수용·시각 목표 달성 여부는 이 문서가 선언하지 않는다. [제작 및 완료 기준](MAP_STORY_DESIGN.md)의 증거로 판정한다.
